# FITWISE 프로젝트 헌장

> 상태: 기준선 v1 · 적용 기간: 2026-10-08 ~ 2027-03-10 · 최종 기준: `main`

이 문서는 FITWISE가 22주 동안 해결할 문제와 만들지 않을 범위를 고정한다. 새로운 아이디어, 기술 또는 팀 과제는 이 문서의 목표와 요구사항에 연결되지 않으면 현재 범위에 넣지 않는다.

## 1. 제품 한 문장

FITWISE는 사용자가 상황·예산·스타일 조건을 입력하면 소수의 의류 후보를 같은 기준으로 비교하고, 추천 이유·주의점·사이즈 근거·보유 의류와의 조합 가능성을 설명해 구매 결정을 돕는 모바일 앱이다.

## 2. 해결할 핵심 문제

온라인 의류 구매자는 상품을 발견한 뒤에도 사이즈·핏, 목적 적합성, 여러 후보의 차이와 기존 옷과의 조합을 직접 판단해야 한다. FITWISE는 상품 수를 늘리는 대신 이 판단에 필요한 근거를 한 흐름으로 묶는다.

설문 21건은 문제 우선순위를 정하는 탐색 근거이며 제품 효과의 증명이 아니다. 효과는 동일 과업 경쟁 비교와 5인 사용성 테스트, 이후 비공개 베타의 행동 지표로 검증한다.

## 3. 22주 최종 목표

Android와 iOS에서 동작하는 모바일 우선 MVP를 만들고 다음을 측정한다.

- 사용자가 상황과 예산을 입력해 후보 3개를 얻는다.
- 사용자가 후보의 추천 이유, 주의점, 사이즈·핏 근거와 신뢰도를 이해한다.
- 사용자가 동일 기준으로 후보를 비교하고 하나를 선택한다.
- 사용자가 대표 보유 의류를 연결해 조합 가능성을 확인한다.
- 결정 시간, 완료율, 선택 확신도, 근거 이해도와 상품 이동 의향을 기록한다.

공개 데모는 완성된 대형 쇼핑 플랫폼이 아니라, 위 의사결정 흐름과 검증 결과·한계를 재현 가능하게 보여주는 결과물이다.

## 4. 변경할 수 없는 P0 사용자 흐름

```text
상황·예산 입력
  → 구조화된 조건 확인·수정
  → 필수 조건을 통과한 후보 3개
  → 이유·주의점·사이즈 근거·신뢰도 확인
  → 동일 기준 비교
  → 후보 선택·저장·제외 피드백
  → 대표 보유 의류와 조합 확인
```

P0 흐름을 방해하거나 완료 전에 별도의 제품 영역을 만드는 기능은 보류한다.

## 5. 범위

### 이번 22주에 포함

- Expo·React Native 기반 Android/iOS 앱
- FastAPI 요청·응답 계약과 결정적 추천 규칙
- 합성 데이터에서 시작해 권리가 확인된 소규모 상품 카탈로그로 확장
- 최소 프로필, My Wardrobe, 검색, 후보 비교, 근거·신뢰도, 피드백
- PostgreSQL 데이터 이력, Supabase Auth·RLS·Private Storage
- 정상·로딩·빈 결과·오류·재시도·오프라인 상태
- 자동 테스트, CI, 비밀값 검사, 오류 관제, 삭제·복구 검증
- 5인 사용성 테스트와 8명 이상 비공개 베타

### 검증 후에만 포함

- 유사 체형 후기 신호: 익명화·권리·품질 조건이 충족될 때만 도입
- LLM 의도 구조화와 설명 초안: 결정적 필터·점수의 보조 역할로만 도입
- 실제 상품 피드: 제공 조건, 이미지 권리, 최신성·삭제 계약이 확인된 공급자만 연결

### 이번 22주에서 제외

- 결제·주문·반품·정산과 ERP 전체 기능
- 무단 브랜드 상품·이미지·후기 크롤링
- 얼굴·전신 사진 기반 체형 추정과 AR 가상 착용
- AI가 가격·재고·실측·후기를 생성하는 기능
- 웹 앱 동시 개발, 쇼핑몰 계정 자동 연동, 대규모 트래픽 최적화

웹은 모바일 P0 흐름이 5인 사용성 테스트와 비공개 베타에서 기준을 통과한 후, 같은 API 계약을 재사용하는 별도 후속 단계다.

## 6. 성공과 실패 판정

목표 수치는 4주차 PRD에서 기준선과 함께 확정한다. 그전에는 아래 항목을 측정 대상으로만 사용하고 성과처럼 표현하지 않는다.

| 관점 | 핵심 지표 | 실패 시 조치 |
|---|---|---|
| 사용자 가치 | 결정 시간, 완료율, 선택 확신도 | 입력·비교 흐름을 축소하거나 재설계 |
| 이해와 안전 | 근거 이해도, 오해·과신 사례 | 문구·신뢰도 표현·경고 구조 수정 |
| 차별화 | 기존 방식 대비 선택 이유 | 차별화 문장 또는 P0 문제 재선정 |
| 재방문 | 옷장 연결, 재사용 의향 | 구매 후 루프의 우선순위 재검토 |
| 사업성 | 상품 이동·지불 의향 | 제휴·구독 가설 보류 또는 변경 |
| 기술 | 필터 위반률, 근거 일치율, 재현성 | 출시 차단 후 규칙·데이터 수정 |

## 7. 단계 게이트

| 게이트 | 통과 조건 | 통과 전 금지 |
|---|---|---|
| G1 · 문제 기준선 | 설문 분석, 경쟁 6개 동일 과업, 우선 문제·차별화·반증 조건 | 기능 확장, 실제 상품 연결 |
| G2 · PRD | P0/P1/P2, 비목표, 지표·이벤트·실패 기준 승인 | DB·인증의 제품 구현 |
| G3 · 프로토타입 | 5명 중 4명 이상 핵심 과업 완료 또는 실패 원인·수정안 확정 | 앱 기능 범위 확대 |
| G4 · 기반 | 인증·RLS·데이터 소유권·카탈로그 출처·삭제 테스트 통과 | 개인 데이터 베타 수집 |
| G5 · 결정 엔진 | 필터 결정성, 근거·주의점·신뢰도, 고정 평가셋 통과 | 추천을 정확하다고 홍보 |
| G6 · 베타 출시 | 보안·접근성·성능·복구·관제와 사람 검수 통과 | 공개 배포 |

게이트를 통과하지 못하면 일정을 맞추기 위해 품질 조건을 삭제하지 않는다. P1/P2 기능을 줄이거나 다음 단계 일정을 조정한다.

## 8. 요구사항 우선순위

- **P0**: 없으면 핵심 의사결정 흐름을 검증할 수 없는 요구사항
- **P1**: P0의 반복 사용·품질·운영을 강화하는 요구사항
- **P2**: 데이터와 사용자 행동으로 필요성이 확인된 뒤 추가하는 요구사항
- **Out**: 이번 22주 범위 밖의 기능

요구사항 ID와 수용 기준은 [제품 요구사항 기준선](requirements.md)에서 관리한다.

## 9. 범위 변경 규칙

새 기능이나 기술을 추가하려면 Issue 또는 결정 기록에 다음을 남긴다.

1. 해결하려는 사용자 문제와 근거
2. 연결되는 요구사항 ID와 주차
3. 성공·실패를 판단할 행동 또는 검사
4. 개인정보·보안·상품 데이터 영향
5. 추가로 인해 빠지거나 늦어지는 기존 범위

근거 없이 아이디어만 있는 항목은 가설 백로그에 두고 구현 일정에 넣지 않는다. 완료된 작업의 기록은 지우지 않고 요구사항 변경 영향과 대체 결정을 남긴다.

## 10. 완료의 의미

코드 또는 문서를 작성한 것만으로 완료가 아니다. 관련 Issue의 수용 기준, 자동 검사, 개인정보·비밀값 검사, 증빙, 문서 갱신과 PR 반영이 모두 확인되어야 한다. 실기기·사용자 테스트·외부 계정처럼 사람이 필요한 항목은 확인 전까지 `진행 중`으로 유지한다.

## 11. 기준 문서 우선순위

충돌 시 다음 순서로 판단한다.

1. 병합된 GitHub `main`의 프로젝트 헌장과 제품 요구사항
2. 현재 주차 과제와 관련 Issue
3. 승인된 API·데이터·보안 문서
4. 열린 PR의 구현과 검증 기록
5. Notion·Project OS의 상태 요약

Notion과 Project OS는 계획의 원본이 아니며 GitHub 상태를 요약한다.
