# Engineering Quality Plan

## 목적

FITWISE의 데이터, UI/UX, 개인정보 보호, 보안, AX 자동화와 SQL 설계를 하나의 품질 기준으로 연결한다. 기능의 수보다 사용자가 안전하게 결정을 완료할 수 있는지, 결과를 재현하고 복구할 수 있는지를 우선한다.

GitHub Issue와 PR이 구현의 기준이며 Notion은 상태와 링크를 보여주는 개인용 운영 화면으로만 사용한다.

## 품질 축

| 축 | 실패 시 영향 | 출시 전 증빙 |
|---|---|---|
| 데이터 무결성 | 잘못된 가격·재고·사이즈, 추천 근거 훼손 | 제약 조건·수집 검증·복구 테스트 |
| UI/UX | 구매 흐름 중단, 잘못된 선택 | 상태별 화면·접근성·실기기 결과 |
| 개인정보·보안 | 신체정보·옷장 사진·구매 이력 노출 | 권한표·RLS 허용/거부·마스킹·삭제 테스트 |
| AX 자동화 | 근거 없는 추천, 자동 배포 사고 | 버전·평가셋·승인 게이트·대체 경로 |
| SQL·운영 | 중복 주문·재고 불일치·복구 실패 | migration·transaction·실행 계획·restore 결과 |

## 데이터 무결성과 손실 대응

### 저장 원칙

- PostgreSQL을 사용자·상품·추천·피드백의 최종 기준으로 사용한다.
- 핵심 테이블은 UUID 기본키, `created_at`, `updated_at`과 명시적 소유자를 갖는다.
- 검색, 권한과 정합성 판단에 쓰는 값은 JSON 내부에 숨기지 않고 정규 컬럼으로 둔다.
- `NOT NULL`, `UNIQUE`, `CHECK`, 외래키를 애플리케이션 검증보다 먼저 적용한다.
- 가격은 정수 최소 단위와 통화 코드를 함께 저장하고 상품 옵션은 `product_variants`로 분리한다.
- 외부 데이터는 출처, 이용 범위, 수집 시각, 변환 버전과 최신성 상태를 함께 저장한다.

### 수집 검증

수집 데이터는 바로 운영 카탈로그에 반영하지 않는다.

```text
source adapter
  -> raw snapshot
  -> schema validation
  -> normalization
  -> quality rules
  -> quarantine or publish
  -> search index
```

다음 항목은 격리 사유다.

- 동일 공급처·외부 ID의 중복 상품
- 음수 또는 허용 범위를 벗어난 가격
- 통화·카테고리·브랜드·옵션 식별자 누락
- 재고와 판매 가능 상태의 충돌
- 사용 권한이나 이미지 출처를 확인할 수 없음
- 이전 수집 대비 비정상적으로 큰 삭제·가격 변동

### 변경과 복구

- 모든 스키마 변경은 순방향 migration, 호환성 영향과 rollback 또는 roll-forward 절차를 포함한다.
- 데이터 변경 작업은 재실행해도 결과가 중복되지 않도록 idempotency key를 사용한다.
- 주문·재고처럼 함께 성공해야 하는 변경은 하나의 transaction으로 처리한다.
- 자동 백업 성공만으로 복구 가능성을 판단하지 않는다. 비공개 베타 전에 별도 환경으로 restore를 실행한다.
- 복구 기록에는 백업 시각, 복구 시각, 대상 버전, 손실 범위, 무결성 검사와 담당자를 남긴다.

초기 목표는 데이터베이스 도입 시 확정한다. 제안 기준은 핵심 데이터 RPO 24시간 이하, RTO 4시간 이하이며 실제 복구 실험으로 조정한다.

## SQL 설계 규칙

논리 영역은 다음처럼 분리한다.

| 영역 | 대표 데이터 |
|---|---|
| `catalog` | 브랜드, 상품, 옵션, 가격 스냅샷, 데이터 출처 |
| `profile` | 사용자 프로필, 동의 버전, 옷장 아이템 |
| `recommendation` | 요청, 후보 점수, 근거, 신뢰도, 피드백 |
| `commerce` | 향후 주문·재고·반품; 사업 모델 검증 전에는 구현 보류 |
| `audit` | 접근·삭제·정책 변경과 수집 실행 기록 |

쿼리를 작성할 때는 다음 순서를 지킨다.

1. 사용자 흐름과 정렬·필터 조건을 정의한다.
2. 정확성과 권한을 확인하는 테스트를 먼저 작성한다.
3. 실제 실행 계획으로 병목을 측정한다.
4. 측정된 패턴에만 복합 인덱스를 추가한다.
5. 인덱스가 쓰기 비용과 보존 정책에 미치는 영향을 기록한다.

N+1 조회, 무제한 목록, 암시적 시간대, 부동소수점 금액, 문자열로 저장한 구조화 상태를 허용하지 않는다. 모든 시간은 DB에서 UTC로 저장하고 앱에서 사용자 시간대로 표시한다.

## UI/UX 품질 기준

핵심 흐름은 `검색 -> 조건 확인 -> 추천 결과 -> 추천 근거 -> 저장·피드백`이다. 각 단계는 다음 상태를 제공한다.

- 로딩: 중복 제출 방지와 진행 상태 안내
- 빈 결과: 조건을 몰래 완화하지 않고 수정 가능한 조건 안내
- 입력 오류: 잘못된 필드 가까이에 원인과 해결 방법 표시
- API 오류: 안전한 문구, 다시 시도와 `request_id` 제공
- 재시도: 동일 요청·피드백의 중복 저장 방지
- 오프라인: 캐시와 최신 서버 데이터를 시각적으로 구분
- 데이터 부족: 추천 불가 또는 낮은 신뢰도와 부족한 근거 표시

추천 카드에는 가격·통화, 데이터 최신 시각, 목적 적합 근거, 사이즈 근거, 주의점과 신뢰도 의미를 함께 표시한다. 색상만으로 상태를 전달하지 않고 접근성 라벨, 터치 영역, 글자 확대와 Android/iOS 실기기 결과를 확인한다.

## 개인정보와 보안

### 최소 수집과 분리

- 추천에 필요하지 않은 이름, 연락처와 정확한 위치를 수집하지 않는다.
- 신체정보, 옷장 사진, 구매 이력과 추천 원문은 높은 민감도로 분류한다.
- 인증 식별자와 앱 프로필을 분리하고 내부 UUID로 연결한다.
- 옷장 사진은 비공개 버킷에 저장하고 만료되는 서명 URL로만 접근한다.
- 개발·테스트에는 합성 데이터 또는 이용 조건이 확인된 데이터만 사용한다.

### 접근 통제

- 모바일 앱에 서비스 역할 키, DB 비밀번호나 장기 비밀값을 넣지 않는다.
- 서버 권한은 용도별로 분리하고 최소 권한을 적용한다.
- 사용자 소유 테이블은 RLS 허용·거부 테스트와 함께 도입한다.
- 관리 기능은 일반 사용자 API와 분리하고 모든 정책 변경을 audit event로 남긴다.

### 로그·보존·삭제

- 로그에는 `request_id`, 오류 코드, 앱·API·모델 버전만 기본 수집한다.
- 토큰, 검색 원문, 신체정보, 사진 URL과 실제 운영 데이터를 로그·캡처·PR에서 마스킹한다.
- 데이터 사전에 수집 목적, 민감도, 보존 기간, 삭제 규칙과 소유자를 기록한다.
- 계정 삭제는 원본·캐시·스토리지·검색 색인·파생 데이터의 처리 결과를 검증한다.
- 익명 통계를 보존할 경우 재식별 불가능성과 목적을 별도로 승인받는다.

보안 사고가 의심되면 자동 재시도보다 기능 중지, 영향 범위 확인, 비밀값 폐기와 사용자 통지를 우선 검토한다.

## AX 자동화

AX는 AI 호출 하나가 아니라 데이터와 업무 흐름을 검증 가능한 단계로 재설계하는 것을 뜻한다.

```text
수집 -> 검증 -> 표준화 -> 특징 생성 -> 후보 검색
    -> 결정적 점수 계산 -> 근거 생성 -> 사용자 확인
    -> 명시적 피드백 -> 평가 -> 다음 버전
```

### 자동화 가능한 단계

- 허가된 피드의 스키마 검증과 정규화
- 상품 속성 분류 초안과 이상치 탐지
- 자연어 의도의 구조화 초안
- 정해진 점수와 근거를 사용한 설명 초안
- 회귀 평가, 지연·비용·오류율 측정과 리포트 생성

### 사람 승인이 필요한 단계

- 새로운 데이터 제공처와 이용 범위
- 개인정보 수집 목적과 보존 기간 변경
- 추천 가중치·정책의 운영 반영
- 모델·프롬프트·평가셋 기준선 교체
- 배포, 데이터 migration과 대량 수정

모델, 프롬프트, 규칙, 데이터셋과 카탈로그 버전을 추천 결과에 연결한다. AI가 실패하거나 신뢰도가 낮으면 구조화된 조건과 결정적 점수만 반환하며, 가격·재고·사이즈 사실을 생성하지 않는다.

## 측정과 출시 게이트

| 영역 | 핵심 지표 |
|---|---|
| 데이터 | 격리율, 중복률, 누락률, 최신성, restore 성공 |
| 제품 | 결정 완료율, 추천 근거 이해도, 저장·제외율 |
| 추천 | 필터 위반률, 근거 일치율, 안정성, 다양성 |
| 운영 | 오류율, p95 응답시간, 재시도 성공률, 비용 |
| 보안 | RLS 거부 테스트, 비밀값 검사, 삭제 완료율 |

다음 조건을 모두 만족해야 출시 후보로 본다.

- 필수 테스트와 CI가 성공했다.
- migration과 rollback 또는 roll-forward 절차가 검증됐다.
- 백업 데이터를 별도 환경에 실제 복구했다.
- 개인정보·비밀값·권한·로그 마스킹 검사가 통과했다.
- 로딩·빈 결과·오류·재시도·오프라인 상태가 확인됐다.
- 모니터링, 알림과 배포 rollback 경로가 준비됐다.
- PR에 증빙과 알려진 제한이 있고 사람이 최종 승인했다.

실행 방법과 기록 형식은 [테스트 전략](../quality/test-strategy.md)과 [테스트 실행 기록](../quality/test-log.md)을 따른다.
