# FITWISE 팀 프로젝트 명세서

> 문서 상태: 팀 합류용 v1 · 기준 브랜치: `main` · 작업 제출: GitHub Issue → Branch → Pull Request

이 문서는 FITWISE에 새로 참여하는 팀원이 프로젝트의 목적, 현재 범위, 데이터 접근 원칙과 과제 제출 방식을 한 번에 이해하도록 만든 시작 문서다. 실제 요구사항과 구현의 최종 기준은 GitHub의 `main` 브랜치다.

## 1. 프로젝트 한 문장

FITWISE는 사용자가 상황·예산·스타일 조건을 자연어로 입력하면 소수의 의류 후보를 비교하고, **추천 이유·주의점·사이즈 근거·보유 의류와의 조합 가능성**을 설명해 구매 결정을 돕는 모바일 우선 서비스다.

쇼핑몰 전체를 복제하거나 모든 상품을 보유하는 것이 목적이 아니다. 허가된 상품 데이터 안에서 사용자가 여러 화면을 오가며 직접 결합하던 판단 근거를 한 흐름으로 정리하는 것이 핵심이다.

## 2. 현재 검증 근거

2026-10-12 종료된 Google Forms 최종 응답 21건에서 다음 문제가 우선순위로 확인됐다.

| 관찰 | 결과 | 제품에 주는 의미 |
|---|---:|---|
| 구매 결정에 30분 이상 사용 | 71.4% | 결정 시간과 탐색 화면 수를 줄일 가치가 있는지 검증한다. |
| 사이즈·핏이 가장 어려움 | 33.3% | 단정적인 사이즈 추천이 아니라 근거와 데이터 부족 상태를 보여준다. |
| 여러 후보 비교가 어려움 | 28.6% | 동일 기준으로 소수 후보를 비교하는 화면을 우선한다. |
| 유사 체형 후기가 가장 필요 | 33.3% | 충분한 동의·익명화·데이터 품질이 확보되기 전에는 실제 후기 기능을 만들지 않는다. |

현재 결과는 편의표본의 중간 분석이므로 시장 전체의 사실이나 기능 효과로 표현하지 않는다.

## 3. 현재 MVP 범위

### 포함

- 상황과 예산 입력
- 입력값 검증
- Safe·Balanced·Bold 세 추천 전략
- 후보별 추천 이유·주의점·근거 충족도
- 정상·로딩·빈 결과·오류·재시도 상태
- FastAPI 요청·응답 계약과 Swagger/OpenAPI 검증
- 합성 상품 데이터 기반 테스트

### 검증 후 결정

- 사이즈·핏 근거 카드
- 카테고리·색상·핏 태그 기반 보유 의류 조합
- 유사 체형 신호의 범위와 익명화 방식
- 실제 상품 피드 또는 파트너 API 연결

### 현재 제외

- 결제·주문·반품과 ERP 전체 기능
- 얼굴·전신 사진 기반 체형 추정
- 허가받지 않은 브랜드 상품·이미지·후기 크롤링
- AI가 가격·재고·실측·후기를 생성하는 기능
- 운영 사용자 데이터로 개발하거나 화면 캡처를 만드는 행위

## 4. 기술 구조

```text
Expo / React Native / TypeScript
  └─ 검색 입력 · 결과 비교 · 상태 UI
       ↓ HTTPS / JSON
FastAPI / Pydantic
  └─ 입력 검증 · 추천 계약 · 결정적 추천 규칙
       ↓ 향후 도입
PostgreSQL(Supabase) + RLS
  └─ 사용자 소유권 · 상품 출처 · 추천 이력
Private Storage
  └─ 향후 옷장 이미지 · 비공개 버킷 · 서명 URL
```

현재 프로토타입은 데이터베이스 없이 합성 카탈로그로 작동한다. 인증·Supabase·실제 상품은 관련 설계와 허용/거부 테스트를 먼저 PR로 제출한 뒤 도입한다.

## 5. 데이터 공개 등급

팀원에게는 과제 수행에 필요한 최소 데이터만 공유한다. 저장소 접근 권한을 얻었다고 해서 개인 설문 원문이나 운영 데이터 접근 권한까지 생기는 것은 아니다.

| 등급 | 예시 | 저장·공유 위치 | 팀원 접근 |
|---|---|---|---|
| 공개 | README, API 계약, 합성 상품, 비식별 집계 | GitHub | 과제에 필요한 범위에서 가능 |
| 팀 내부 | 와이어프레임, 미공개 일정, 비식별 테스트 메모 | 비공개 Issue·승인된 Notion | 담당 과제에 필요한 사람만 |
| 제한 | 설문 원본, 세션 원문, 상세 오류 로그 | 소유자 제한 저장소 | 기본 접근 금지, 필요 시 별도 승인 |
| 비밀 | API 키, 서비스 역할 키, DB 비밀번호, 토큰 | Secret Manager·로컬 환경변수 | 값 공유 금지, 역할별 실행 권한만 부여 |
| 운영 개인정보 | 계정 식별자, 신체정보, 옷장 사진, 구매 이력 | 암호화된 운영 환경 | 개발 과제에서 사용 금지 |

### 팀원에게 제공하는 데이터

- `services/api/app/catalog.py`의 합성 상품
- 식별자를 제거한 설문 집계와 비율
- 고정된 합성 사용자 입력과 예상 결과
- OpenAPI 요청·응답 예시
- 테스트 전용 이미지 또는 사용 권한이 확인된 자산

### 팀원에게 제공하지 않는 데이터

- Google Forms 개별 응답 원문
- 이름, 이메일, 연락처와 계정 식별자
- 실제 신체 치수, 구매 이력과 옷장 사진
- `.env`, API 키, 토큰, DB 접속 문자열
- 운영 로그와 오류 추적 도구의 원문 이벤트

## 6. 권한 부여 원칙

1. 기본값은 접근 금지다.
2. 저장소는 필요한 팀원에게만 최소 역할로 부여한다.
3. 팀원이 서비스에 접근해야 한다면 개인 계정을 사용하고 공유 계정을 만들지 않는다.
4. 개발·테스트·운영 환경을 분리한다.
5. 배포와 운영 비밀값 변경은 프로젝트 소유자가 수행한다.
6. 권한은 과제 종료, 역할 변경 또는 팀 탈퇴 시 회수한다.
7. GitHub PR·로그·화면 캡처에는 개인정보와 비밀값이 없는지 제출 전에 확인한다.

## 7. 과제는 기능이 아니라 완성 가능한 단위로 배분한다

좋은 과제는 UI 코드 한 조각이 아니라 사용자 가치부터 검증까지 이어지는 작은 세로 단위다.

```text
사용자 문제
  → 화면과 상태
  → API 계약
  → 합성 데이터
  → 권한·개인정보 조건
  → 테스트
  → PR 증빙
```

모든 과제 Issue에는 다음 항목이 있어야 한다.

```markdown
## 사용자 가치

## 구현 범위

## 제공 데이터와 사용 제한

## 보안·개인정보 요구사항

## 완료 조건
- [ ] 정상 상태
- [ ] 로딩·빈 결과·오류·재시도
- [ ] 테스트
- [ ] 개인정보·비밀값 검사
- [ ] 문서와 화면 증빙

## 제외 범위

## 검증 명령

## 제출물
- PR 링크
- 테스트 결과
- 개인정보가 제거된 화면 캡처
- 남은 제한사항
```

## 8. 권장 첫 과제

| 과제 | 담당 범위 | 제공 데이터 | 핵심 완료 조건 |
|---|---|---|---|
| 실기기 상태 검증 | Android/iOS 정상·빈 결과·오류·재시도 | 합성 요청 시나리오 | 재현 단계, 결과, 캡처, 오류 기록 |
| 사이즈 근거 카드 | UI·도메인 타입·부족 상태 | 합성 사이즈와 실측 | 단정 금지, 접근성, 단위 테스트 |
| 후보 비교 개선 | 동일 기준 3개 후보 비교 | 합성 상품 3개 | 도움 없이 비교, 선택 근거 설명 가능 |
| 데이터 사전·ERD v0 | 필드·출처·민감도·보존·삭제 | 합성 스키마 | 소유권과 삭제 규칙 포함 |
| RLS 보안 테스트 설계 | 익명·본인·타인·관리자 접근표 | 합성 사용자 ID | 허용·거부 테스트가 함께 제출됨 |
| CI·오류 기록 자동화 | 검사 결과와 실패 분류 | 비식별 테스트 로그 | 실패를 성공으로 표시하지 않음 |

실제 상품 수집, 운영 데이터, 로그인과 결제 과제는 현재 배분하지 않는다.

## 9. GitHub 작업 절차

1. 관련 Issue와 이 문서의 완료 조건을 읽는다.
2. 같은 범위의 열린 PR과 브랜치가 있는지 확인한다.
3. 기존 작업이 없다면 `<type>/<issue-number>-<short-name>` 브랜치를 만든다.
4. 범위를 벗어나는 작업은 같은 PR에 섞지 않는다.
5. 커밋은 하나의 목적 단위로 작성한다.
6. 포맷·린트·테스트·빌드를 변경 범위에 맞게 실행한다.
7. PR 템플릿에 검증 결과와 남은 작업을 사실대로 기록한다.
8. 리뷰 의견은 새 PR이 아니라 기존 브랜치에 추가 커밋한다.
9. 승인 없이 병합·Issue 종료·브랜치 삭제·배포 변경을 하지 않는다.

### 커밋 예시

- `feat: add size evidence card`
- `fix: handle empty recommendation response`
- `docs: define product data dictionary`
- `infra: add secret scan to ci`

## 10. 로컬 실행과 검증

### 모바일

```bash
cd apps/mobile
npm ci
npm run lint
npm run typecheck
npm test
npm run start
```

### API

```bash
cd services/api
python -m venv .venv
# 가상환경 활성화 후
python -m pip install -r requirements-dev.txt
python -m pytest -q
python -m uvicorn app.main:app --reload
```

- Swagger UI: `http://127.0.0.1:8000/docs`
- OpenAPI: `http://127.0.0.1:8000/openapi.json`

실제 비밀값은 로컬 `.env` 또는 승인된 Secret Manager에서만 설정한다. 저장소에는 값이 없는 `.env.example`만 커밋한다.

## 11. PR 제출 기준

PR에는 반드시 다음 내용이 포함돼야 한다.

- 관련 Issue: `refs #번호`
- 변경한 기능과 주요 파일
- 기존 동작과 달라진 점
- 실행한 검사 명령과 결과
- 테스트 개수와 알려진 경고
- 실행하지 못한 검사와 이유
- 개인정보가 제거된 화면 또는 결과 문서
- 사람 확인이 필요한 항목

다음 중 하나라도 있으면 제출 상태를 `통과`로 바꾸지 않는다.

- CI 실패
- 타인 데이터 접근 가능성
- 비밀값 또는 개인정보 노출
- 데이터 손상이나 삭제 실패
- 근거 없이 생성된 가격·재고·실측·후기
- 정상 상태만 있고 빈 결과·오류·재시도 검증이 없음

## 12. 신규 팀원 첫날 체크리스트

- [ ] 이 문서와 `AGENTS.md`를 읽었다.
- [ ] 담당 Issue, 범위와 제외 범위를 확인했다.
- [ ] 공유받은 데이터가 합성·비식별 데이터인지 확인했다.
- [ ] 로컬에서 모바일 또는 API 테스트를 실행했다.
- [ ] 실제 개인정보와 비밀값을 사용하지 않는다는 원칙을 확인했다.
- [ ] 첫 PR을 병합하지 않고 리뷰 요청 상태로 제출했다.

## 14. 문의와 의사결정

- 기능 요구가 불명확하면 Issue에 질문을 남긴다.
- 개인정보·권한·외부 데이터 사용 여부가 불명확하면 구현을 멈추고 프로젝트 소유자 확인을 받는다.
- 실제 구현 내용은 GitHub PR에 기록하고, Notion과 Project OS에는 담당자·Issue·PR·테스트·막힌 점과 현재 상태만 기록한다.
- 프로젝트 소유자는 제품 범위, 운영 권한, 실제 데이터 사용과 최종 병합을 결정한다.
