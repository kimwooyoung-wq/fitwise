# FITWISE 5인 사용성 테스트 계획과 기록표

> 상태: 준비 완료 · 대상 빌드: PR #4 `검색 → 추천 결과` 프로토타입 · 실제 테스트 결과는 측정 후 기록한다.

## 목적

설문 21건에서 확인된 `사이즈·핏 판단`, `여러 후보 비교`, `흩어진 정보 결합` 문제를 현재 프로토타입이 실제로 줄이는지 확인한다. 추천 정확도나 시장성을 증명하는 테스트가 아니라, 사용자가 도움 없이 핵심 흐름을 이해하고 안전하게 판단할 수 있는지 검증한다.

## 참가자와 개인정보 원칙

- 최근 6개월 안에 온라인으로 의류를 구매한 성인 5명 이상을 모집한다.
- 가능하면 구매 빈도가 낮은 사람과 높은 사람을 섞는다.
- 이름, 연락처, 얼굴, 음성과 화면 녹화는 필수로 수집하지 않는다.
- 참가자는 `P01`~`P05`처럼 임의 번호로만 기록한다.
- 실제 신체 치수나 구매 이력 대신 참가자가 선택한 범주 또는 합성 정보를 사용한다.
- 테스트 결과는 GitHub와 Notion에 집계·비식별 형태로만 남긴다.

## 시작 안내문

> 오늘은 참가자를 평가하는 것이 아니라 FITWISE 화면을 평가합니다. 막히거나 이해되지 않는 부분은 그대로 말씀해 주세요. 테스트 중단을 원하면 언제든 중단할 수 있습니다. 이름, 연락처, 실제 신체 치수는 기록하지 않으며 결과는 익명 번호로만 정리합니다.

## 비교 조건

각 참가자는 같은 구매 상황을 두 방식으로 수행한다. 순서 효과를 줄이기 위해 홀수 참가자는 기존 방식부터, 짝수 참가자는 FITWISE부터 시작한다.

| 조건 | 수행 방식 |
|---|---|
| A · 기존 방식 | 평소 사용하는 쇼핑몰·검색 방식으로 후보를 찾고 하나를 선택한다. |
| B · FITWISE | 합성 상품을 사용하는 프로토타입에서 상황·예산을 입력하고 추천 후보와 근거를 확인해 하나를 선택한다. |

## 공통 구매 상황

> 예산 10만 원 이하로 이번 주말 저녁 약속에 입을 상의를 찾는다. 기존에 가진 검정 슬랙스와 어울려야 하며, 너무 붙는 핏은 피하고 싶다.

실제 브랜드·가격·재고가 아닌 합성 데이터임을 시작 전에 알린다.

## 과업

| 번호 | 참가자에게 제시할 과업 | 관찰 항목 | 성공 기준 |
|---|---|---|---|
| T1 | 상황과 예산 조건을 입력해 추천을 시작해 주세요. | 입력 항목 이해, 검색 시작 위치, 오류 | 도움 없이 검색 완료 |
| T2 | 추천된 후보를 비교하고 가장 적합한 하나를 골라 주세요. | 후보 비교 방식, 외부 정보 탐색, 결정 시간 | 후보 3개 중 하나 선택 |
| T3 | 선택한 이유와 구매 전 주의할 점을 설명해 주세요. | 추천 근거·주의점 이해 | 근거와 주의점 합계 2개 이상 설명 |
| T4 | 사이즈 정보가 충분한지 판단하고, 부족하다면 다음 행동을 말해 주세요. | 과도한 확신, 데이터 부족 표시 인지 | 부족 상태에서 단정하지 않음 |
| T5 | 보유한 검정 슬랙스와 어울릴지 판단해 주세요. | 조합 정보 위치, 이해도 | 조합 가능 여부와 근거 설명 |

진행자는 참가자가 30초 이상 멈췄을 때만 `현재 무엇을 찾고 계신가요?`라고 묻는다. 기능 위치나 정답은 알려주지 않는다.

## 측정값

| 지표 | 기록 방법 |
|---|---|
| 과업 성공 | 도움 없이 성공 / 도움 후 성공 / 실패 |
| 결정 시간 | 조건별 시작부터 최종 선택까지 초 단위 |
| 비교 효율 | 확인한 화면·외부 페이지 수 |
| 선택 확신 | 수행 전과 후 각각 1~5점 |
| 근거 이해 | 참가자가 설명한 올바른 근거·주의점 개수 |
| 사이즈 안전성 | 데이터 부족을 인지하고 추가 확인 행동을 선택했는지 |
| 오류·마찰 | 발생 화면, 행동, 기대, 실제 결과, 재현 여부 |
| 재사용 의향 | 동일한 구매 상황에서 다시 사용할 의향 1~5점 |

조건 수행 순서: A→B / B→A

[조건 A · 기존 방식]

## 중단 기준

- 실제 개인정보 입력이나 외부 전송이 요구되는 경우
- 실제 결제·주문으로 이어질 가능성이 있는 경우
- 다른 사용자의 데이터가 보이는 경우
- 앱이 반복적으로 종료되거나 핵심 과업 진행이 불가능한 경우

중단 사유는 `docs/quality/test-log.md`에 비식별 상태로 기록하고 심각한 보안 문제는 기능을 중지한 뒤 수정·재검증한다.

## 분석 방법

1. 참가자별 원본 메모에서 식별 가능 정보를 제거한다.
2. 조건 A와 B의 결정 시간 중앙값, 화면 수, 확신도 변화를 비교한다.
3. 과업 성공률과 근거 이해 개수를 집계한다.
4. 반복된 마찰을 `탐색`, `비교`, `사이즈`, `설명`, `조합`, `오류`로 코딩한다.
5. 아래 판정표로 기능별 다음 결정을 내린다.

| 판정 | 기준 | 다음 행동 |
|---|---|---|
| 유지 | 4/5 이상 도움 없이 성공하고 중대한 안전 문제가 없음 | MVP PRD에 반영 |
| 수정 후 재검증 | 2~3/5 성공 또는 같은 마찰이 2명 이상에게 반복 | UI·문구 수정 후 동일 과업 재실행 |
| 제외·보류 | 0~1/5 성공, 가치 설명 불가, 개인정보·데이터 비용이 효용보다 큼 | MVP에서 제외하거나 추가 증거 수집 |
